# Persisted experiment drafts

An experiment configuration can now become a PostgreSQL record. Creating a draft does not schedule work, call an LLM, or execute a scenario.

## Interface

| Endpoint | Behavior |
| --- | --- |
| `POST /experiments/validate` | Existing validation-only endpoint; unchanged |
| `POST /experiments` | Validate, commit a draft, return HTTP 201 with the saved record |
| `GET /experiments?limit=20&offset=0` | Read a bounded page, ordered by creation time descending and UUID descending for ties |
| `GET /experiments/{id}` | Read one UUID; return 404 if it is absent or 422 if malformed |

List limits must be 1–100; offsets must be nonnegative. The frontend shows the latest 20 drafts, loads them on mount, refreshes after a successful save, and provides a manual refresh button. Loading, empty, and error states are explicit.

## One table

| Column | Type | Purpose |
| --- | --- | --- |
| `id` | UUID primary key | Stable identifier, generated when inserting a row |
| `name` | varchar(80), required | Human-readable label; names need not be unique |
| `agent_version` | varchar(80), required | A label for a future agent configuration, not yet a foreign key |
| `scenarios` | JSONB, required | Small configuration array; not separately managed entities yet |
| `status` | varchar(16), default `draft` | Explicitly records that execution has not started |
| `created_at` | timestamp with time zone | Database-generated creation time; indexed for recent-record queries |

Database constraints enforce required fields, nonblank names/version labels, scenario array type/count, and draft-only status. Pydantic additionally checks supported scenario keys, duplicates, input lengths, and unknown fields. There is no agent registry to reference yet; introducing one will require an intentional schema change and migration.

JSONB keeps this configuration small and easy to read as one record. If scenarios become independently versioned or frequently queried objects, separate tables and foreign keys will be more appropriate. The creation-time index supports the current recent-first query; indexes also consume storage and add write work.

## Request model versus database model

`schemas.py` defines what HTTP requests and responses contain. `models.py` maps Python objects to database columns. They solve different boundary problems; accepting a request does not itself insert a row.

## Sessions and transactions

The SQLAlchemy engine owns a connection pool. `get_session` yields a fresh session for each request and closes it afterward. A session coordinates ORM work; it is not a global shared transaction.

The create route opens a short transaction, adds the object, flushes SQL, refreshes database-generated values, and commits when the transaction block exits. An exception rolls the transaction back. A successful 201 response is returned only after commit. Read requests close their sessions too.

`expire_on_commit=False` keeps the loaded response values available after commit, avoiding an extra implicit reload while serializing the response. `pool_pre_ping` helps detect stale pooled connections after a database restart. Neither setting makes interrupted writes safe to retry automatically.

Database errors produce a generic 503 response. Internal error types are logged without returning database details to the browser. Validation remains available even if the database is offline because that route does not request a database session.

## Migrations

Alembic records schema revisions. The initial migration creates the table, constraints, and index. The application does not call `create_all` on startup. Run `uv run alembic upgrade head` explicitly before serving a new schema.

`alembic.ini` locates migrations. `migrations/env.py` connects Alembic to model metadata and the configured database. `script.py.mako` is the template for future revisions; `versions/` contains the actual changes. Autogenerated migrations must be reviewed before use. `uv run alembic check` detects model/schema drift.

The initial downgrade drops the experiments table and its data. It is for deliberate development rollback, not routine production operation.

## Failure semantics

The browser uses a 10-second save timeout. A lost response can occur after the transaction commits. Therefore an error says the save could not be confirmed and asks the user to refresh saved experiments before retrying. There are no automatic write retries or idempotency keys yet. Repeating a successful POST creates another draft, even with the same name.

The UI validates response shapes at runtime before rendering stored records. Read requests are bounded and cancel on component cleanup; an old response cannot overwrite a newer refresh. The API URL remains browser-visible, while the database URL is backend-only.

## Local development and tests

The included bootstrap uses existing native PostgreSQL tools to initialize an isolated cluster under ignored `backend/.local/`, listening only on `127.0.0.1:55432`. The example credentials and initial superuser are for this local cluster; deployed databases need their own credentials and restricted application role. No cloud services are used.

Tests use a separate database whose name must end in `_test`, apply real Alembic migrations, and isolate each test inside a rolled-back outer transaction. Request sessions use savepoints so route commits do not leak test data. Tests cover creation/retrieval across sessions, pagination, invalid requests, missing IDs, failed-commit rollback, database failure responses, and a database constraint. See the backend README for setup.
